## Как выбирались source-узлы

Волна 08 не брала страницу только потому, что в её исходном JSON было `links: []`.

Дополнительно были вычтены source-slug всех bridge-файлов волн 01–05.

Таким образом, выбранные страницы одновременно:

1. не имели собственных прямых ссылок в исходной записи;
2. не были уже прошиты поздним `zzzz01–20` bridge-файлом;
3. имели существующую человеческую сцену, в которую можно вести без создания нового URL.

## Инфраструктура релиза

Во время накопления волн 06–08 проявилась отдельная причина лишних проверок: Pages workflow использовал `concurrency.group: pages` вместе с `cancel-in-progress: false`.

Это заставляло GitHub сохранять устаревший релиз в `waiting`, а более свежие состояния ставить за ним в очередь, хотя новый `main` уже включал прежние изменения.

В объединённом пакете параметр изменён на:

`cancel-in-progress: true`.

Теперь при новом push в `main` устаревший Pages-run той же concurrency-группы должен отменяться, а проверяться и публиковаться только последнее состояние корпуса.

Это не отменяет полного release build. Оно убирает повторную проверку уже superseded-состояний.

## Архитектурный вывод

После восьми волн видно две разные операции сети:

1. **прошить тупик**;
2. **сделать уже существующий переход точнее**.

Они должны чередоваться.

Иначе можно либо получить много формально связанных карточек без смысловой глубины, либо очень глубокую сеть вокруг небольшой части корпуса.

ONTOS.RENT становится фондом именно в сочетании:

**ширина достижимого пространства + конкретность следующего хода**.
